## P1 发现

### P1-1 返回栈与实际跳转不匹配：列表 → 播放 → 返回会掉进用户没见过的详情页

- **文件:行号**：`ui/MainViewModel.kt:645-677`（`back()`），配合 `ui/NbaLiveApp.kt:276-279`、`ui/NbaLiveApp.kt:290-293`、`ui/NbaLiveApp.kt:367-371`、`ui/MainViewModel.kt:365-378`（`playMatch`）
- **严重度**：P1
- **问题**：
  列表页点比赛卡/hero 卡/"立即观看"、直播页点卡片、搜索结果点结果，走的都是 `viewModel.playMatch(m)`。`playMatch` 直接把 `_route` 从 `LIST` 置成 `PLAYER`（`MainViewModel.kt:376`），**没有经过 `DETAIL`**。但 `back()` 处理 `Route.PLAYER` 时无条件 `_route.value = Route.DETAIL`（`MainViewModel.kt:650`）。
  于是实际的栈是 `LIST → PLAYER`，而返回键按的是 `PLAYER → DETAIL`。用户从列表点进去看球，按返回，落到"赛事详情"页（一个他从未见过的中间页），再按一次才回列表。
  `NbaLiveApp.kt:275` 的注释"点比赛直接全屏自动播放，不再先跳详情页选线路"说明跳过详情页是**有意设计**，那么返回时补一个详情页就是遗漏，不是设计。
- **触发条件**：任何一条"列表/直播/搜索 → 播放"的入口，按返回键或播放页左上角返回按钮（`NbaLiveApp.kt:242`）。"同时在播"面板切场（`NbaLiveApp.kt:340` `onLiveMatchClick = viewModel::playMatch`）后返回同理，且此时详情页内容是**切过去的那一场**，更容易让人迷惑。
- **建议修法**：给 `PlayerUiState`（或 ViewModel 内一个字段）记录"进入播放页时来自哪个路由"，`back()` 按来源回退：
  ```kotlin
  // playMatch / openPlayer 里
  playerEnteredFrom = _route.value   // LIST 或 DETAIL
  // back() 里 Route.PLAYER 分支
  _route.value = playerEnteredFrom
  ```
  注意 `openPlayer`（详情页点线路）的来源是 `DETAIL`，`playMatch` 的来源是 `LIST`，两者行为不同，不能用同一个常量。

### P1-2 Hero 卡上的 70% / 92% 白字与"立即观看"胶囊对比度不达标（2.85:1 ~ 4.07:1）

- **文件:行号**：`ui/screens/MatchListScreen.kt:286`（`background(GradLiveOnWhite)`）、`:296`（联赛名 `Color.White.copy(alpha = 0.92f)`）、`:318`（"VS" `Color.White.copy(alpha = 0.7f)`）、`:346` + `:361`（"立即观看"胶囊 `Color.White.copy(alpha = 0.22f)` 底 + 纯白字）
- **严重度**：P1
- **问题**：
  `GradLiveOnWhite` 已经做了 `whiteTextSafe` 压暗，**纯白字**确实是 4.50~4.53:1（刚好踩线达标）。但卡片上并不是纯白字：
  - `:318` 的 "VS" 用 70% 白 → 实测 **2.85:1 ~ 3.05:1**（三档渐变取值不同），远低于 AA 4.5:1；
  - `:296` 的联赛名用 92% 白 → **4.03:1 ~ 4.07:1**，也不达标；
  - `:346` 的胶囊底是 22% 白叠在渐变上，把底色提亮成 `#C4845A`~`#E8586D`，上面压纯白字只有 **3.09:1 ~ 3.47:1**。
  也就是说：压暗函数把底色调到达标线，紧接着的半透明白字又把对比度还回去了。这是典型的"修了底色没修前景"。
- **触发条件**：列表页顶部有直播中的比赛（hero 卡出现）时，任何主题下都成立；暗色下更明显。
- **建议修法**：hero 卡上不要用 alpha 白，改用不透明的高亮色；或按同样思路做一个"白字安全"的前景常量：
  ```kotlin
  // 把 0.7/0.92 这类透明度换成不透明色，例如
  color = Color.White            // VS 也直接用纯白
  // 胶囊底改为更深的一档，保证白字 >= 4.5
  color = Color(0x33000000)      // 或直接复用 HeroPill 的 20% 黑（实测 6.4:1）
  ```
  `HeroPill`（`:399` 的 `Color(0x33000000)`）实测白字 6.4:1，是达标的，说明"黑底"这条思路在这个渐变上是可行的——胶囊改用同一配方即可。

### P1-3 浅色主题下系统导航栏图标仍是白色，在浅色背景上不可见

- **文件:行号**：`ui/theme/Theme.kt:294-299`
- **严重度**：P1
- **问题**：
  `NbaLiveTheme` 的 `SideEffect` 只设置了 `isAppearanceLightStatusBars`，**没有设置 `isAppearanceLightNavigationBars`**。`MainActivity.kt:44` 的 `enableEdgeToEdge()` 用的是无参默认值，其 `navigationBarStyle` 是 `SystemBarStyle.auto(...)`，判断依据是**系统的** `uiMode`，不是 App 内的 `darkMode` 开关。
  于是：系统处于深色模式 + 用户在「我的」里切到浅色主题 → 导航栏拿到深色 scrim + 白色图标，而 App 背景是 `#EDF0F8`，三个虚拟键几乎看不见。
- **触发条件**：系统深色模式，App 内切浅色主题（`ProfileScreen` 的深色模式开关或顶栏主题按钮）。反向（系统浅色 + App 深色）同样错，只是表现为深色导航栏配深色图标。
- **建议修法**：在同一个 `SideEffect` 里补齐导航栏，并且与状态栏用同一个 `darkTheme` 值：
  ```kotlin
  SideEffect {
      val window = (view.context as? Activity)?.window ?: return@SideEffect
      val controller = WindowCompat.getInsetsController(window, view)
      controller.isAppearanceLightStatusBars = !darkTheme
      controller.isAppearanceLightNavigationBars = !darkTheme   // 补这一行
  }
  ```
  更彻底的做法是切主题时重新调用一次 `enableEdgeToEdge(statusBarStyle = ..., navigationBarStyle = ...)`，把 scrim 也一起换掉（当前浅色主题下导航栏 scrim 仍是深色系）。

### P1-4 联赛筛选胶囊上的场次计数用 80% 白，对比度 3.35:1

### 导航状态机

#### P2-1 在非默认标签页按返回键会直接退出 App

- **文件:行号**：`ui/NbaLiveApp.kt:202`
- **严重度**：P2
- **问题**：`BackHandler(enabled = !inPip && (searchOpen || route != Route.LIST || fullscreen))`。当 `route == LIST` 且 `tab` 是 `LIVE` 或 `PROFILE` 时，enabled 为 false，返回键交给系统 → 退出 App。用户预期是"回到赛事标签页"。
- **触发条件**：切到"直播"或"我的"标签，按返回。
- **建议修法**：把 `tab` 纳入判定，并优先回默认标签：
  ```kotlin
  BackHandler(enabled = !inPip && (searchOpen || route != Route.LIST || fullscreen || tab != Tab.MATCHES)) {
      when {
          searchOpen -> searchOpen = false
          route == Route.PLAYER && !PlayerLock.backExitsPlayer(playerLocked) -> Unit
          fullscreen -> fullscreen = false
          route != Route.LIST -> viewModel.back()
          else -> tab = Tab.MATCHES
      }
  }
  ```

#### P2-2 路由状态没有 SavedStateHandle，进程重建后从播放页掉回列表

- **文件:行号**：`ui/MainViewModel.kt:149`（`private val _route = MutableStateFlow(Route.LIST)`）、`:152`、`:175`
- **严重度**：P2
- **问题**：`route`/`listState`/`detailState`/`playerState` 都是普通 `MutableStateFlow`，没有 `SavedStateHandle`。进程被杀后重建：`route` 回到 `LIST`，`playerState.match` 为 null，播放中断。直播流本身无法恢复（地址带时效签名），这点可以接受；但**用户在播放页被回收后回来会直接落在列表**，且 `tab`/`fullscreen` 这些 UI 态反而被 `rememberSaveable` 恢复了，两类状态的重建语义不一致。
- **触发条件**：播放中切后台，被系统回收后从最近任务恢复。
- **建议修法**：至少把 `route` 与 `match.id` 存进 `SavedStateHandle`，重建后回到 `DETAIL`（而不是 `PLAYER`），让用户看到"线路列表 + 重新播放"，而不是无声地回到列表。UI 侧状态（`tab`/`fullscreen`/`searchOpen`）建议一并收敛到 ViewModel 的 SavedStateHandle，避免两套恢复机制并存。

#### P2-3 `tab` 与 `route` 是两个互不知情的状态机

- **文件:行号**：`ui/NbaLiveApp.kt:113`（`tab`）、`:266-304`（`when (tab)` 只在 `Route.LIST` 分支内生效）、`:251-255`（切换标签时补一次 `viewModel.back()`）
- **严重度**：P2
- **问题**：`tab` 是 Composable 本地状态，`route` 在 ViewModel。`route != LIST` 时 `tab` 被冻结但保留；切标签时用"顺手调一次 back()"来对齐两者。这种"两个状态机 + 一个补救动作"在后续加页面时很容易漏。例如未来若允许从「我的」跳到详情，`back()` 只回 `LIST`，`tab` 仍是 `PROFILE`，页面内容与选中标签就会错位。
- **触发条件**：目前只在详情页点底部标签时触发（`route != LIST` → `back()`）。
- **建议修法**：把"当前标签"并入 ViewModel 的单一导航状态（`data class NavState(val tab: Tab, val route: Route)`），`back()` 和标签点击都只改这一个状态。

#### P2-4 无深链支持（结论：当前不需要，但 `onNewIntent` 是死代码）

#### P2-5 `Route.DETAIL` 分支用 `return@Box` 兜底，缺 match 时整块空白

### 副作用 / LaunchedEffect

#### P2-6 `syncAutoEnterEnabled` 依赖 DisposableEffect 先于 LaunchedEffect 执行

- **文件:行号**：`ui/NbaLiveApp.kt:165-177`（DisposableEffect 写 `PipState.setPlayerActive`）、`:182-185`（LaunchedEffect 调 `activity?.syncAutoEnterEnabled()`）、`MainActivity.kt:93-95`（`syncAutoEnterEnabled` 读 `PipState.playerActive.value`）
- **严重度**：P2
- **问题**：`syncAutoEnterEnabled()` 读的是进程级单例 `PipState.playerActive`，而不是从 Compose 侧传参。它之所以能读到正确值，靠的是"同一次组合中 `DisposableEffect`（:165）排在 `LaunchedEffect`（:182）之前执行"这个 Compose 副作用排队顺序。这个顺序是稳定的，但**两个 effect 之间的数据依赖完全靠声明顺序隐式保证**，中间任何一次重构（调整声明位置、把其中一个抽成独立 Composable）都会静默破坏它，症状是"自动进小窗偶尔不生效"。
- **触发条件**：重构 `NbaLiveApp` 的副作用顺序时。
- **建议修法**：让 `syncAutoEnterEnabled` 接受显式参数，或把两段合并成一个 effect：
  ```kotlin
  LaunchedEffect(route, playingNow, playerState.playbackDead) {
      val active = PipState.shouldAutoEnterPip(route == Route.PLAYER, playingNow)
      PipState.setPlayerActive(active)
      activity?.syncAutoEnterEnabled(active)   // 参数化，不再读全局
      if (playerState.playbackDead) activity?.finishPipIfBroken()
  }
  ```

#### P2-7 错误 Snackbar 会被下一条错误取消

- **文件:行号**：`ui/NbaLiveApp.kt:216-220`
- **严重度**：P2
- **问题**：`LaunchedEffect(route, playerState.errorId)` 里 `snackbarHostState.showSnackbar(it)` 是挂起调用，会一直占用该协程直到 Snackbar 消失。当 `errorId` 再次自增（`MainViewModel.kt:184-185` 的 `withError` 每次都 +1）时，effect 重启 → 上一个 `showSnackbar` 的协程被取消 → **前一条错误提示提前消失**。故障切换场景下（"线路2 不可用，已自动切换" 紧跟 "网络错误"）用户可能只看到最后一条。
- **触发条件**：播放页短时间内连续上报两次以上错误（`onPlaybackFailed` 的 `play()` 递归重试路径容易连发）。
- **建议修法**：若希望逐条展示，用 `LaunchedEffect` 收集到一个 `Channel`/`SharedFlow` 后顺序消费；若只想显示最新一条，就在 effect 里显式 `snackbarHostState.currentSnackbarData?.dismiss()` 再 show，把"覆盖"变成有意行为而不是取消副作用。

#### P2-8 列表页"今天/明天"标签不会跨零点自动更新（注释与实现不符）

- **文件:行号**：`ui/screens/MatchListScreen.kt:203-213`（注释与 `val today = LocalDate.now(...)`、`remember(gridMatches, today)`）、`:78-83`（`dayLabel`）
- **严重度**：P2（**待确认**：是否真需要自动更新）
- **问题**：`:209-211` 的注释写"标签在渲染时现算，App 跨零点后不用切走页面标签也会自动变成新的今天"。但 `today` 只在**组合**时求值，跨零点本身不会触发任何重组——如果列表页静止不动（无滚动、无状态变化），标签会一直停在旧值，直到下一次重组（用户滑动、刷新、切标签）。也就是说注释承诺的行为需要外部事件驱动才成立。
  另外 `LocalDate.now(ZoneId.systemDefault())` 在 `:212` 每次重组都调用一次，而 `MatchFormat.kt:26` 已经缓存了 `systemZone`，这里没有复用。
- **触发条件**：App 停在列表页跨过零点且无任何交互。
- **建议修法**：要么用 `produceState` + 定时器（每分钟/到零点）驱动 `today`：
  ```kotlin
  val today by produceState(LocalDate.now(systemZone)) {
      while (true) { delay(60_000); value = LocalDate.now(systemZone) }
  }
  ```
  要么把注释改成"跨零点后下一次重组时自动修正"，不要承诺做不到的行为。
